## D1 — chiaroscuro #1 · receipt-gap + correctness (Lane D token accounting)
**Files:** `tools/token_stream.py`, `tools/token_stream_receipt.json`, PR body Lane D.

> Two arithmetic notes on Lane D, both checkable from the committed files:
>
> 1. **Body vs receipt.** The PR body states "1280x theoretical compression", but
>    `tools/token_stream_receipt.json` records `bytes_per_window.compression_tokens = 12.8`
>    (and `compression_svd_floor = 40.0`). One of the two is a typo — worth pinning so the
>    committed number and the prose can't diverge later.
> 2. **Token granularity.** `encode()` returns one id per point, and `P_train` is
>    `(NUM_CELLS, K_SVD)` = 7200 points — i.e. **one token per cell per window**. The byte
>    accounting charges `NUM_CELLS * WINDOW * bits` = one token per cell *per frame*, a 60×
>    larger denominator than the encoder emits. If the intended unit is per-cell-window, the
>    token-vs-raw compression is ~768× not 12.8×; if per-frame, the encoder needs a token per
>    frame. Either way the code and the accounting currently disagree by a factor of `WINDOW`.
>
> Not a verdict on the method — the SVD-floor note is the right caveat — just the two numbers
> that a later reader will trip on.

*(Intent: the receipt is the artifact; a body/receipt mismatch is exactly the class their own
doctrine says to never ship.)*
