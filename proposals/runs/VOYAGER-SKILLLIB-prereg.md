# VOYAGER-SKILLLIB — A MINIMAL VOYAGER-STYLE SKILL LIBRARY, NO GAME ENV

Lane **VOYAGER-SKILLLIB**. Mechanism lifted from **Voyager** (arXiv:2305.16291,
Wang et al. 2023) minus the Minecraft environment: the *growth engine* is a
**verified-program library** — generate candidate programs, gate them through an
**executable verifier**, store the survivors with **embeddings**, and on a later
task **retrieve + reuse** the nearest verified program. Capability accumulates
with **zero weight updates** (no gradient step anywhere in this lane).

## The booked question

Can a *verified* program library, retrieved by semantic similarity, **beat
generation-from-scratch** on held-out tasks — on CPU, 6 GB VRAM, zero metered
spend — while **never** admitting an unverified program?

Domain (chosen so verification is pure code, deterministic, and instant): small
Python function synthesis. Each task = `(id, family, spec, oracle, argkind)`.
The **oracle is code**; the verifier executes the candidate against test cases
generated by the oracle. **No LLM judge anywhere in the verification path.**

## Frozen gates

**(a) RETRIEVAL** — On the held-out query set, **top-1 retrieval family-hit rate
≥ 0.60**, and **≥ 0.20 above the chance baseline** `1/F` (F = 4 families →
baseline 0.25). Secondary, non-gating read: mean cosine similarity of
same-family pairs **strictly greater** than cross-family pairs.

**(b) REUSE** — On the held-out task set, **pass@k (k = 8) for
retrieval-augmented generation > pass@k for scratch generation**, by **≥ 0.10
absolute**, with **≥ 1 task flipped fail → pass**. (Verbatim-reuse — running the
retrieved program unchanged — is logged as a secondary read; it is expected to
lose and cannot by itself satisfy gate (b).)

**(c) PURITY** — The library **only ever stores VERIFIED programs**: on load, and
on every append, every entry must carry `verified == true` plus a recorded
passing test result. **Zero unverified entries.** A deliberately-wrong program
fed to the verifier must be **rejected** (negative control), and an attempt to
append an unverified entry must **raise**.

## Arms (frozen)

| arm | what it does | gating |
|---|---|---|
| `store` | generate → verify → append verified program + nomic embedding | feeds (a),(c) |
| `scratch` | generate k=8 fresh candidates per held-out task, verify each | (b) control |
| `augmented` | retrieve top-1 skill, put its spec+code in the prompt, generate k=8, verify | (b) treatment |
| `verbatim` | run the retrieved program unchanged on the held-out task | (b) secondary |

Generation: temperature **0.2** (storage pass), **0.8** (pass@k arms), per-sample
seed = `31415 + i`. Verifier: candidate exec'd in a restricted namespace, 3 s
SIGALRM wall-clock guard, mismatch/exception/timeout ⇒ **FAIL**. An entry is
stored **only** on all-pass.

## What would falsify

Gate (a) fail means the embedding space does not separate task families at all
(retrieval is noise). Gate (b) fail means verified-program retrieval buys nothing
over a cold 3B model on this domain — the Voyager loop's value is then in
*long-horizon composition*, not single-task transfer, and cannot be claimed from
this prototype. Gate (c) fail voids the lane outright.

## Named risks (before fire)

1. **6 GB VRAM is not the binding constraint here — CPU/serial generation is.**
   70 generation calls at ~3–8 s ≈ the whole wall clock. On the *full* Voyager
   loop the binding risk is the **verifier**, not the model: an executable
   verifier strong enough to gate open-ended skills is exactly what a
   game/state-rich domain gives you for free and a text domain does not. Weak
   verifiers ⇒ the library fills with plausible-but-wrong skills and the loop
   silently degrades (gate (c) is necessary but not sufficient).
2. Embedding-collision retrieval errors (two families share idioms) — logged as
   the same-family-vs-cross-family similarity margin.
3. Restricted-namespace exec is not a real sandbox; acceptable only because
   candidates come from a local model on a local box and are never networked.
